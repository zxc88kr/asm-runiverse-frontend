## 1. 문서 — 어느 것이 정본인가

### 1-1. 화면을 만들 때 보는 문서는 둘뿐이다

> **화면 레이아웃·배치** → `와이어프레임_최종.md`
> **화면 시각(간격·색·상태)** → Figma `Ds2URinGrgXo43wC5OFQ8x`

`../Docs/UI화면설계_md/Runiverse_와이어프레임_최종.md` (2026-07-31). 끝에 **화면 인벤토리 표**가 있고
각 화면 절에 ASCII 레이아웃 + 컴포넌트 리스트가 있다. `[변경]` 표기는 수정(1) 대비 달라진 항목이다.

**Figma에서 잰 픽셀값이 디자인 시스템과 다르면 문서가 이긴다.**

## 2. 매칭 — MVP 범위

**MVP의 매칭은 예약 매칭이다.** 2~4명 자동 매칭.

### 2-1. 사용자가 고르는 프리셋은 2개뿐이다

| 프리셋 | 값 |
|---|---|
| **시간 슬롯** | `18:00`~`22:00`, **30분 단위** — 18:00 · 18:30 · … · 21:30 · 22:00 (9슬롯) |
| **목표 거리** | `3km` · `5km` · `10km` — `PresetChip` 3개 고정 |

**날짜는 고르지 않는다. 오늘만이다.** 오늘/내일 탭은 최종본에서 삭제됐다.
시간은 칩이 아니라 **바텀시트 스크롤 리스트**로 고르고, 각 슬롯에 `N명 대기`를 함께 보여준다
(`--color-match-waiting`). 대기 인원은 사회적 증거로 슬롯을 유도하는 장치라 빼면 안 된다.

**페이스 수준은 고르지 않는다.** 온보딩(S04)에서 입력한 프로필 기록을 바탕으로 자동 반영된다.
화면 문구도 그렇게 되어 있다 — "페이스 수준은 프로필 기록을 바탕으로 자동으로 맞춰드려요".
매칭 알고리즘은 페이스를 쓰지만 **선택 UI로 노출하지 않는다.**

### 2-3. S04 페이스는 등급이 아니라 숫자다 `[정본 이탈]`

와이어프레임 최종본 S04는 `(입문)(중급)(숙련)(잘 모르겠어요)` 프리셋이다.
**구현은 이걸 따르지 않는다.** 5km 기준 **1km당 분·초**를 휠로 받는다.

| | 이유 |
|---|---|
| 왜 숫자인가 | '중급'의 뜻은 사람마다 다르다. "1km를 6분에" 는 누구에게나 같은 값이다 |
| 왜 5초 단위인가 | 스스로 신고하는 값에 1초 정확도는 의미가 없다. 59칸을 굴리게 하면 고르기가 일이 된다 |
| 안 재본 사람은 | `아직 몰라요` 출구를 준다. **기본값으로 때우지 않는다** — 그 숫자가 그대로 시그니처 컬러가 된다 |

등급이 사라진 게 아니라 **숫자에서 파생된다.** `features/onboarding/domain/pace_level.dart`가
그 구간을 쥐고 있고, 시그니처 컬러 hue와 홈의 연습 유도가 같은 값을 읽는다.

> ⚠️ **구간 경계는 확인이 필요하다.** `5'00"` 미만 숙련 / `6'30"` 미만 중급은
> 아마추어 5km 기록(25분·32분 30초)을 보고 **개발자가 정한 값**이다. 기획 확정값이 아니다.

`PaceLevel.unmeasured`와 `beginner`는 `needsPracticeNudge`가 참이다.
홈(S05)에서 **혼자 연습하기**를 권할 대상이고, 그 연습이 미측정 값을 채운다.
재본 적 없는 사람이야말로 한 번 뛰어봐야 하는 쪽이라 미측정도 포함한다.

### 2-2. 그 밖의 제약

- 실시간 즉시 매칭은 **1차 확장**이다. 지금 만들지 않는다.
- **지역은 매칭 조건이 아니다** (원격 매칭이므로).
- 조건은 프리셋으로만. 자유 입력을 허용하면 조합이 흩어져 매칭 성사율이 떨어진다.
- 시그니처 컬러는 매칭 등록 직전에 확인·변경할 수 있다("오늘 가져갈 내 색"). 색이 실제로 의미를 갖는 순간이 여기여서, 프로필에만 두면 대부분 기본값으로 매칭하게 된다.

## 3. 색 시스템 — 가장 틀리기 쉬운 부분

### 3-1. 색은 feature 3개에 걸친다

색 리빌 · 프로필 오라 · 기록 캘린더. 의존 규칙에 예외를 만들지 말고 **역할로 나눈다.**

| 위치 | 역할 |
|---|---|
| `core/widgets/color/` | `Color`를 **파라미터로 받아** 그리기만 하는 순수 표현 위젯 |
| `features/color/` | 지표→색 매핑, 팔레트, 컬렉션 같은 도메인 로직과 전용 화면 |

### 3-2. 러닝 색은 테마가 아니라 데이터다

한 화면에 여러 개가 동시에 뜬다(기본 컬렉션은 30색). **ThemeExtension에 넣지 말고 위젯 파라미터로 전달한다.**

→ `core/theme/`의 `AppGlow`가 이 규칙을 타입으로 강제한다. 글로우 메서드는 전부 `Color runColor`를 받고,
`AppElevation`에는 색을 받는 API가 없다. 앱 크롬에 러닝 색이 새지 않는다.

### 3-3. 글로우와 elevation은 역할이 다르다 — 섞지 않는다

- `glow.*` = 러닝 색이 발광하는 표현. `elevation.*` = 면의 높이 위계를 나타내는 중립 그림자.
- `glow`는 반드시 **색을 인자로 받는 형태**(`glow.md(runColor)`)로 만들어, 앱 크롬에 실수로 쓸 수 없게 한다.
- `Material(elevation:)` 단축 경로가 둘을 섞기 가장 쉬운 지점이다.

### 3-4. 글로우를 텍스트 뒤에 깔지 않는다

러닝 중 수치는 대비 **7:1**을 만족해야 하는데, 숫자 뒤 색 번짐이 이를 무너뜨린다.

### 3-5. 색만으로 정보를 전달하지 않는다

컬렉션 슬롯엔 hue 이름 + 획득 수(2/3), 셰이드 스와치엔 셰이드 번호(1/2/3),
매칭 상태엔 색 점 + 상태 문구, 격차 수치엔 부호(`+`/`−`)를 병기한다. (색맹 대응)

**이모지는 제품 UI에 쓰지 않는다.** 상태·성취는 색 + 텍스트 + 스트로크 아이콘으로 표현한다.
예외는 로비의 사용자 리액션 — 그건 사용자 발화다.

## 4. 러닝 화면 (S11~S13)

- 터치 타깃 **56px** (그 외 화면은 44px)
- 파괴적 액션은 탭이 아니라 **hold-to-end(2초) 또는 2단계 확인**으로만
- ⚠️ **`FontFeature.tabularFigures()`는 폰트가 `tnum`을 지원하지 않으면 Flutter가 조용히 무시한다.** 에러도 경고도 없다.
  <br>→ **2026-07-31 검증 완료.** OTF 바이너리의 `tnum` 태그 존재 + 실제 렌더링 동작을 모두 확인했다
  (`00:11:47`에서 `1`이 고정폭으로 벌어지는 것을 육안 확인). 다시 확인할 필요 없다.
  단, 폰트 파일을 교체하면 재확인한다. 토큰은 `AppTypography.metricHero/Lg/Md`에 이미 적용돼 있다.

## 5. Riverpod / 라우팅 함정

### 5-1. 숨은 탭의 provider는 실제로 dispose된다

매칭 상태를 홈 화면 안에 두면 **탭을 옮기는 순간 타이머와 WebSocket 구독이 끊긴다.**
→ 전역 매칭 상태는 `keepAlive`를 명시하고, **글로벌 스티키 배너와 홈 히어로가 같은 하나의 provider를 구독**한다.

### 5-2. `redirect` 안에서 `ref.watch`를 쓰지 않는다

무한 리빌드가 난다. `refreshListenable`을 쓴다.

### 5-3. 그 외

- 5탭은 `StatefulShellRoute`로 구성해 탭 전환 시 스크롤·상태를 보존한다.
- 탭 아이콘은 **Lucide 계열 2px 스트로크**, 활성 탭만 primary blue (와이어프레임_최종 C1).
- 글로벌 매칭 스티키 배너는 **Shell 레이어에 1개만.** 화면마다 복붙 금지.
  <br>**홈 탭에서는 띄우지 않는다** — 홈은 히어로가 매칭 상태를 전담하므로 중복이다 (C2).
  <br>위치는 탭바 바로 위. 확정·실패 배너는 순간 토스트를 놓쳤을 때의 **상시 진입점** 역할이라 사라지지 않는다.
- 알림 딥링크는 매핑 테이블 1곳으로 관리하고, 대상이 없으면 홈으로 폴백한다.
- **UI는 상태를 계산하지 않는다.** 페이스 환산, 상위 % 산출, 히스테리시스 판정은 `domain/`이나 provider에 둔다.
- Stream 구독(GPS, WebSocket)은 반드시 `ref.onDispose`에서 취소한다.
- 상태 전체를 watch하지 말고 **필요한 필드만 `select`** 한다. 러닝 화면은 초당 여러 번 갱신되므로 전체 watch는 화면 전체 리빌드가 된다.

## 6. 환경 관련 실제 고장 사례

| 증상 | 원인 | 조치 |
|---|---|---|
| `flutter analyze`가 분석 서버 크래시로 죽음 | 저장소가 **한글·공백이 든 경로**에 있음 | ASCII 경로로 옮긴다 |
| `main.dart` 교체 후 컴파일 자체가 안 됨 | `test/widget_test.dart`가 `flutter create` 기본 카운터 테스트라 `MyApp`을 직접 import | **교체하는 커밋에서 함께 지우거나 다시 쓴다** |
| `checkDebugAarMetadata`에서 빌드 실패 · `compileSdk of at least 37` | 패키지가 **compileSdk 37**을 요구하는데 Flutter 3.44.8 기본값이 36이다 | 그 패키지의 **버전을 낮춰 고정한다.** `flutter_secure_storage`(11.x 금지)·`permission_handler`(13.x 금지)가 같은 이유로 묶여 있다. 캐럿(`^`)을 쓰면 다음 사람의 `pub upgrade`에서 다시 깨지므로 정확한 버전으로 박는다 |
| `flutter test integration_test`가 5분 타임아웃 | 끝나면 **앱을 제거**한다. 다시 설치되며 런타임 권한이 날아가고, 앱이 권한 다이얼로그를 띄운 채 아무도 안 누른다 | 도는 동안 `adb shell pm grant <pkg> android.permission.ACCESS_FINE_LOCATION`을 1초마다 반복해서 준다 |
| 테스트가 끝난 뒤 기기 DB를 못 뽑음 | 같은 이유다. 앱 전용 폴더가 앱과 함께 사라진다 | 도는 동안 `adb exec-out run-as <pkg> cat databases/<파일>`로 빼낸다. `run-as`로 `/sdcard`에 복사하는 것은 **앱 UID에 저장소 권한이 없어 실패한다** |

## 7. 함께 고쳐야 하는 짝

아래가 바뀌면 **같은 커밋에서** 짝을 맞춘다. 안 맞추면 다음 사람 PC에서 빌드가 깨진다.

| 바뀐 것 | 같이 고칠 곳 |
|---|---|
| `.fvmrc` 버전 | `.vscode/settings.json`의 `dart.flutterSdkPath` (`fvm use <버전>`이 대신 갱신해 주기도 한다) |
| `main.dart` 교체 | `test/widget_test.dart` |
| `assets/` 파일 추가 | `pubspec.yaml`의 `assets:` / `fonts:` 블록 (선언 없이는 번들되지 않는다) |
| 앱 식별자(org) | `android/app/build.gradle.kts`와 iOS `Runner.xcodeproj/project.pbxproj` **양쪽** |
| `pubspec.yaml` 의존성 | 이 문서 / `CLAUDE.md`의 Tech Stack |
| **비밀번호 규칙** (백엔드 `SignUpRequest`의 `@Size`·`@Pattern`) | `lib/features/auth/domain/password_rule.dart` + `AppStrings.authPasswordGuide` 등 문구 4개 |
| `PasswordRule`의 규칙 | `FakeAuthRepository.seedPassword` — 씨앗 계정이 자기 규칙에 걸리면 로그인 시험을 못 한다 |
| **`GeoPoint`의 필드** | `LocationSmoother.smooth()` — 새 `GeoPoint`를 만들어 돌려주므로 빠뜨린 필드가 조용히 `null`이 된다 (11-2) |

`lib/` 밖에서 앱이 쓰는 것은 `assets/fonts/`(Pretendard) 하나다.

비밀번호 규칙은 **물어볼 API가 없어서** 앱과 서버 두 곳에 같은 값이 있다.
서버가 바꾸면 증상은 **"앱은 통과시켰는데 서버가 400"**이다.

## 8. 기타 제약

- 피드 공개 범위(팔로워/전체/나만)는 **UI만 만들고 서버 필터를 안 걸면 안 된다.**
- 소셜 로그인 시크릿은 **서버 보관이 원칙.** 클라이언트에 두지 않는다.
- 인증 순서: 이메일 인증 기반 로컬 로그인 → 소셜(구글·카카오).
- **기술 리스크 1순위는 백그라운드 GPS 추적과 다중 사용자 실시간 동기화다.** 다른 화면보다 먼저 프로토타입으로 검증한다.

## 9. 인증 — 로그인·가입

설계 근거 전문은 `docs/specs/2026-08-04-local-auth-design.md`, 백엔드와 주고받을 것은
`Runiverse_인증_협업문서.md`에 있다. 여기에는 **나중에 사고가 되는 것**만 적는다.

### 9-1. 화면 순서

```
S01 스플래시 ─┬─ 로그인 상태 ──────────────────────────────→ 홈
              └─ 아니면 → S02 소개 3장 → 로그인(S02.5)
                                          ├─ 로그인 성공 ──────→ 홈
                                          └─ 가입하기
                                             → 가입1 S03 약관
                                             → 가입2 정보 입력 (자동 로그인)
                                             → 가입3 S04 프로필 → 홈
```

**약관이 정보 입력보다 앞이다.** 순서가 반대면 동의를 묻기도 전에
이메일·비밀번호가 서버에 저장된다.

이동 방식도 여기 매여 있다.
- 소개 → 로그인은 `go`. 되돌아갈 이유가 없어 **로그인 화면에는 뒤로가기가 없다.**
- 로그인 → 약관 → 정보 입력은 `push`. 뒤로가기로 되짚을 수 있고,
  되짚어도 **동의한 것이 남아 있다**(화면이 트리에 살아 있다).
- 정보 입력 → 프로필은 `go`. 계정이 이미 만들어졌으므로 되돌아가면 안 된다.

### 9-2. 로그인 화면 하나에 방식 셋을 합쳤다 `[정본 이탈]`

**정본:** 와이어프레임 S02.5는 카카오·애플·이메일 **버튼 셋과 하단 링크**뿐이다.
이메일·비밀번호를 입력받는 화면은 정본에 없다.

**실제:** 한 화면에 이메일·비밀번호 입력 + `또는` 구분선 + 카카오·애플 버튼 + 가입 링크다.
방식 선택 화면을 따로 두면 탭이 한 번 더 필요한데, 고를 것이 셋뿐이라 다 보이는 편이 짧다.

**왜 이메일 입력이 필요한가:** 백엔드가 `POST /auth/signup` · `POST /auth/login`을
이메일·비밀번호로 받는다.

**카카오·애플 버튼은 지우지 않았다.** 눌리고, "아직 준비 중이에요"를 띄운다.
회색으로 잠그면 앱이 미완성으로 읽힌다 — 피드·대회일정 탭과 같은 원칙이다.

⚠️ **로그인·정보 입력 두 화면은 Figma에 없다.** 여백·타이포는 확인받지 않은 값이다.

### 9-3. 온보딩 여부는 서버가 안다

**서버가 `isOnboarded`를 준다.** 추측하지 않는다 — 로그인 응답에 담겨 오고, 앱은 그것을
토큰과 함께 저장한다. 프로필 등록을 마치면 `POST /api/v1/users/onboarding`으로 서버에 반영한다.

갈림길을 쓰는 곳은 둘이고 **같은 기준을 써야 한다.**

| 어디 | 무엇을 보나 |
|---|---|
| 스플래시 | 저장된 `isOnboarded` (갱신 응답에는 이 값이 없다) |
| 로그인 화면 | 로그인 응답의 `isOnboarded` |

한쪽만 고치면 **로그인 직후에는 홈, 앱을 껐다 켜면 프로필 등록**으로 가는 어긋남이 생긴다.
실제로 겪었고 `sign_in_page_test`가 그것을 잡는다.

> 예전 방식(**가입한 사람은 신규, 로그인한 사람은 기존**)은 지웠다. 앱을 지웠다 깔면
> 기존 사용자가 프로필을 다시 보던 구멍이 있었는데, 이제 서버가 기억한다.

⚠️ **갱신(`POST /auth/refresh`) 응답에는 `isOnboarded`가 없다.** 그래서 자동 로그인
경로에서는 저장된 값이 유일한 근거다. 다른 기기에서 온보딩을 마쳐도 이 기기는 모른다 —
전송을 시도하면 409 `ALREADY_ONBOARD`가 오고, 저장소가 그것을 성공으로 흡수하면서 맞춰진다.
`ReissueResponse`에 `isOnboarded`가 추가되거나 조회 API가 생기면 이 구멍이 닫힌다.

### 9-3-1. 서버 `code`는 API마다 다르다

같은 400인데 `code`가 갈린다. **상태 코드를 1차 근거로 삼는다.**

| API | 400일 때 `code` |
|---|---|
| `POST /auth/login` · `/auth/refresh` | `VALIDATION_FAILED` |
| `POST /auth/email/verifications` · `.../confirm` | **`INVALID_REQUEST`** |
| `POST /users/onboarding` | `INVALID_REQUEST` · 몸통이 깨지면 `MALFORMED_REQUEST_BODY` |

`code`로만 갈랐다면 온보딩 400이 전부 `unknown`으로 떨어졌을 것이다.

⚠️ **같은 `/auth` 아래에서도 갈린다.** 이메일 인증 두 경로는 `VALIDATION_FAILED`가
아니라 `INVALID_REQUEST`다 — 2026-08-10 서버 응답으로 확인했다. 그래서
`HttpAuthRepository._failureOf`는 **두 코드를 함께** 본다. 하나만 보면 나머지가
`unknown`이 되어 "로그인하지 못했어요"라는 엉뚱한 문구가 뜬다.

### 9-3-2. `/users/me`가 `isOnboarded`의 유일한 출처다

```
access 토큰이 있으면 → GET /api/v1/users/me

인증 직후 (가입 · 이메일 로그인 · 카카오)  → isOnboarded ? 홈 : 프로필 등록(S04)
자동 로그인 (스플래시)                      → 홈  (유도 카드가 isOnboarded로 켜진다)
```

#### 왜 로그인 응답의 값을 쓰지 않는가

로그인 응답에도 `isOnboarded`가 실려 온다. 그것은 **로그인하던 순간의 사진**이다.
저장해 두면 다른 기기에서 프로필을 채웠을 때 이 기기의 값이 낡은 채로 남아,
자동 로그인이 유도 카드를 헛되이 띄운다. 갱신 응답에는 토큰 둘뿐이라 스스로 낫지 않는다.

**값이 갈리는 곳을 둘로 두지 않는다** — 로그인 직후에도 `/me`를 부른다.
`AuthController._loadCurrentUser()` 한 곳이 그 일을 하고, `restore()`와
`_authenticate()`가 함께 부른다.

⚠️ **`/me`가 실패해도 로그인을 되돌리지 않는다.** 인증은 이미 성공했다. 부가 요청
하나가 실패했다고 로그인 화면으로 돌려보내면 *네트워크가 잠깐 끊긴 것*과 *비밀번호가
틀린 것*이 같은 결과가 된다. 그때는 로그인 응답으로 세운 상태를 그대로 둔다.

#### 인증 직후와 자동 로그인이 갈린다

**앱을 열자마자 입력 폼이 뜨는 것은 당황스럽다.** 그래서 폼으로 *보내는* 것은
**인증 직후**뿐이다. 자동 로그인은 홈으로 간다.

로그인 화면의 둘(이메일 · 카카오)은 `_goAfterSignIn()` 한 곳을 공유한다. 나누면
"로그인 방식에 따라 도착지가 다르다"는 규칙이 생기고, 한쪽만 고치는 사고가 난다.

⚠️ **카카오는 가입과 로그인이 한 경로다.** 계정이 없으면 서버가 그 자리에서 만들고
`isOnboarded=false`로 답한다. 그래서 카카오 첫 로그인은 이메일의 *가입*에 해당하고,
같은 규칙이 그것을 폼으로 보낸다.

**이탈한 사람이 손으로 다시 로그인하면 폼을 다시 본다.** 서버가 보기에 처음 오는
사람과 구분되지 않기 때문이다(`/me`도 이건 못 가른다).

#### ⚠️ 홈으로 가도 관문이 막아선다 — `AppShell`

자동 로그인이 홈으로 보낸다고 앱을 쓸 수 있는 것은 아니다. `AppShell`이
`isOnboarded == false`면 **닫히지 않는 시트**를 세운다(§10-5).

**탭마다 두지 않는다.** `StatefulShellRoute.indexedStack`은 한 번 연 탭을 살려두므로
탭마다 띄우면 시트가 겹쳐 쌓인다. 셸에 하나만 두면 다섯 탭이 같은 관문을 지난다 —
홈만 막으면 다른 탭으로 돌아 들어갈 수 있다.

### 9-4. 서버에 붙었다 — 다만 토큰은 아직 메모리다

`AuthRepository`(도메인 인터페이스)에 답하는 것은 `HttpAuthRepository`다. dio로 실제 서버를 부른다.
바꾼 곳은 `auth_provider.dart` **한 줄**이고, 화면과 `AuthController`는 손대지 않았다.

`FakeAuthRepository`는 지우지 않았다 — 서버 없이 도는 테스트가 계속 쓴다.
⚠️ **씨앗 계정 `test@runiverse.app` / `runi123!`은 이제 테스트 안에서만 유효하다.**
앱에서 그 계정으로 로그인하면 서버에 없으므로 실패한다.

| 지금 | 나중 |
|---|---|
| `authRepositoryProvider` → `HttpAuthRepository` | — |
| `tokenStoreProvider` → `InMemoryTokenStore()` | `flutter_secure_storage`를 쓰는 구현 |

⚠️ **토큰은 여전히 메모리라 앱을 끄면 사라진다. 자동 로그인은 아직 동작하지 않는다.**
로그아웃 UI도 없어서, 로그인 화면으로 돌아가려면 앱을 다시 띄우는 수밖에 없다.

⚠️ **`signOut`은 서버를 부르지 않는다.** 저장소가 `accessToken`을 들고 있지 않아 실을 자리가 없다.
로컬 토큰은 지워지지만 **서버 `refreshToken`은 만료까지 살아 있다** — 기기를 잃어버렸을 때 끊을 방법이 없다.

#### 붙일 때 반드시 걸리는 것 셋

**서버 주소를 안 넘기면 앱이 멈춘다.** `--dart-define=API_BASE_URL=...` 없이 빌드하면
네트워크 계층이 `StateError`로 죽는다. 기본값을 두지 않았다 — 기본값은 결국 소스에 적힌 주소다.
`String.fromEnvironment`는 `const`라 **핫 리로드로는 안 바뀐다.**
주소를 고쳤는데 그대로면 이것부터 의심한다.

**에뮬레이터 안의 `localhost`는 에뮬레이터 자신이다.** 개발 PC는 따로 정해진 주소로 불러야 한다.
이걸 모르면 서버가 멀쩡한데 연결 거부만 보이고, **앱 코드를 아무리 봐도 원인이 안 나온다.**

**Android는 API 28부터 평문 HTTP를 막는다.** 개발 서버에 TLS가 없으면 코드가 맞아도 요청이 안 나간다.
허용은 `android/app/src/debug/AndroidManifest.xml`에만 뒀다 —
`src/main`에 넣으면 **릴리스 빌드의 보호까지 사라진다.**

#### 통신 로그에 본문을 찍지 않는다

dio의 `LogInterceptor`는 요청·응답 본문을 통째로 찍는다.
요청에는 **비밀번호**가, 응답에는 **`refreshToken`**이 들어 있다.
대신 method·경로·상태 코드만 남기는 인터셉터를 달았고, 디버그 빌드에서만 돈다.

```
[api] → POST /api/v1/auth/login
[api] ← 200 /api/v1/auth/login
[api] x badResponse 401 /api/v1/auth/login
```

### 9-5. 비밀번호 허용 문자는 앱이 서버보다 좁다

앱은 **영문·숫자·특수문자만** 받는다(`PasswordRule`). 서버 `SignUpRequest`의 정규식은
앞의 lookahead 셋으로 종류를 요구하지만 **본체가 `.{6,16}`이라 한글도 통과시킨다.**

방향이 이쪽인 것은 안전하다 — 앱이 통과시킨 값은 서버도 통과한다. 400이 날 일이 없다.

⚠️ 다만 **서버를 좁히지 않으면** 다른 클라이언트(curl, 웹, 나중의 관리자 도구)로
한글 비밀번호 계정을 만들 수 있고, 그 계정은 이 앱의 가입 화면 기준으로는 만들 수 없는 계정이 된다.
로그인 화면은 비밀번호 형식을 안 보므로 들어오기는 한다.

백엔드에 **정규식 본체를 같은 문자 집합으로 좁혀 달라**고 요청해 둔다.

판정 순서도 정해져 있다 — **허용 문자 → 길이 → 종류.**
한글을 친 사람에게 "6자 이상이어야 해요"부터 말하면 한글을 더 치게 된다.

### 9-6. 401 재시도를 붙일 때 반드시 막아야 하는 것 셋

인터셉터는 아직 없다. 저장소마다 401을 직접 다룬다.

**2번은 `TokenRefresher`(`features/auth/domain/`)가 맡는다.** 진행 중인 갱신이 있으면
새로 부르지 않고 그것을 기다린다. ⚠️ **아직 두 곳만 그것을 쓴다** —
`HttpRunningRoomRepository`와 WebSocket이다. 러닝을 시작하면 그 둘이 **같은 만료
토큰으로 거의 동시에** 나가 실제로 겹치기 때문이다.

나머지 네 곳(`onboarding` · `profile` × 2 · `settings`)은 아직 `_auth.refresh`를 직접
부른다. 서로 동시에 나갈 일이 없어 미뤄 뒀다. **손대는 김에 하나씩 옮긴다.**

`core`에 두지 않은 이유는 `AuthRepository`를 알아야 해서다 — `core → features`는
뒤집힌 방향이다. 쓰는 쪽에는 함수 하나만 넘긴다(`WsAccessToken`).

1. **`/auth/login`의 401은 재시도하지 않는다.** 로그인 실패가 401이라, 그냥 두면
   비밀번호를 틀릴 때마다 refresh를 부른다. `signup` `login` `refresh` 세 경로를 건너뛴다.
2. **refresh를 동시에 두 번 부르지 않는다.** 백엔드 `ReissueHandler`가 해시 불일치를
   **탈취로 보고 리프레시 토큰을 지운다.** 401이 동시에 여러 개 나면 두 번째 호출이 이미 회전된
   토큰을 보내고, **잘못 없는 사용자가 로그아웃된다.** `Future<bool>?` 하나를 공유해 한 번만 부른다.
3. **재시도한 요청이 또 401이면 멈춘다.** 아니면 무한 루프다.

### 9-7. 이메일 인증 티켓 — 실패해도 소비된다

가입은 세 단계다. 발송 → 확인(**티켓을 받는다**) → 가입(**티켓을 보낸다**).
이메일은 티켓 안에 들어 있어 가입 요청이 따로 받지 않는다.

| # | 엔드포인트 | 요청 | 성공 |
|---|---|---|---|
| 1 | `POST /auth/email/verifications` | `{email}` | 204 |
| 2 | `POST /auth/email/verifications/confirm` | `{email, code}` | `{verificationTicket}` |
| 3 | `POST /auth/signup` | `{verificationTicket, password}` | 201 + **토큰** |

**가입 응답이 토큰을 준다.** 예전처럼 signup 뒤에 login을 이어 부르지 않는다.

#### ⚠️ 티켓은 1회용이고, 가입이 실패해도 소비된다

서버 `SignUpHandler`가 `consume(ticket)`을 **먼저** 하고 계정을 만든다. Redis라
롤백도 없다. 이미 가입된 이메일로 거절당했어도 그 티켓은 이미 없다.

**그래서 가입 실패에 "다시 시도" 버튼을 주면 안 된다.** 두 번째는 반드시
`EMAIL_NOT_VERIFIED`가 나고, 사용자는 같은 조작에 이유가 바뀌는 것만 본다.
실패하면 티켓을 버리고 인증 단계를 다시 연다.

`FakeAuthRepository.signUp`도 **같은 순서**여야 한다. 계정 검사를 먼저 하면
실패했을 때 티켓이 남아, 실제 서버에선 안 되는 재시도가 테스트에서만 통과한다.

#### ⚠️ 인증 여부를 이메일 비교만으로 판정하면 구멍이 있다

`bool _verified` 하나로 두면 A로 인증받고 B로 가입하는 구멍이 생긴다. 그래서
가입 화면은 **인증한 이메일 자체**를 담고 현재 입력과 비교한다.

**비교만으로도 부족하다.** A로 인증 → B로 고침(티켓을 버린다) → 다시 A로 되돌리면
비교식은 통과하는데 손에 든 티켓이 없다. 가입 버튼이 열리는데 눌러도 아무 일이
없다. 판정은 **티켓의 존재도 함께** 봐야 한다.

#### 이미 가입된 이메일은 발송 단계에서 막힌다

인증번호를 치기 전에 알 수 있다. 다 치고 나서 알려주면 한 일이 통째로 버려진다.

⚠️ 2026-08-10 배포본에는 이 검사가 없어 가입 단계에서야 409가 났다. 앱은 새 동작을
기준으로 만들었고, **가입 단계의 `EMAIL_ALREADY_EXISTS` 처리도 남겨 뒀다** —
발송과 가입 사이에 다른 사람이 먼저 가입하는 경합이 있다.

#### 카운트다운 5분은 앱의 가정이다

서버 `codeTtl`은 설정값이고 응답에 실리지 않는다. **만료 판정은 절대 화면
타이머로 하지 않는다** — 서버가 `EMAIL_VERIFICATION_NOT_FOUND`로 알려준다.
확인 응답에 `expiresIn`을 실어 달라고 요청해 뒀다.

#### ⚠️ `EMAIL_SEND_FAILED`는 503이다

`HttpAuthRepository._failureOf`가 상태 코드보다 `code`를 먼저 보는 이유가 이것이다.
5xx를 먼저 `server`로 자르면 이 사유가 영영 나오지 않는다. 상태 코드는 **아는
`code`가 없을 때만** 쓰는 마지막 수단이다.

#### 가입 화면 테스트는 `tokenStoreProvider`를 반드시 override한다

빠뜨리면 **가입 성공 경로에서만** 멈춘다. `SecureTokenStore`가 부르는 플랫폼
채널이 테스트에 없어 예외가 나는데, 그것은 `AuthException`이 아니라 잡히지 않고
`_submitting`이 `true`로 남는다. 스피너가 영원히 돌아 `pumpAndSettle`이 끝나지
않는다. **실패 경로는 저장소를 부르지 않아 멀쩡히 통과하므로** 원인을 찾기 어렵다.


### 9-8. 카카오 로그인 — 앱은 토큰을 만지지 않는다

앱이 하는 일은 둘뿐이다. **① 인가 코드와 `codeVerifier`를 얻고 ② 서버에 넘긴다.**
토큰 교환도 프로필 조회도 서버(`KakaoOauthClient`)가 한다.

```
POST /api/v1/auth/oauth/kakao
{"authorizationCode": "...", "codeVerifier": "..."}
→ 200 {userId, accessToken, refreshToken, isOnboarded}
```

⚠️ **흔한 예제를 그대로 쓰면 안 된다.** `UserApi.instance.loginWithKakaoTalk()`은
**액세스 토큰을 앱이 받는다** — 이 서버와 맞지 않는다. 써야 하는 것은
`AuthCodeClient.authorize()`이고, 그것은 인가 코드만 돌려준다.

#### ⚠️ `redirect_uri`는 앱이 고를 수 없다

`auth_platform_native.dart`가 `redirectUri != KakaoSdk.redirectUri`면
`ClientErrorCause.notSupported`로 거절한다. 그래서 앱은 주소를 조립하지 않고
`KakaoSdk.redirectUri`(`kakao<네이티브앱키>://oauth`)를 그대로 쓴다.

**서버 `oauth.kakao.redirect-uri`가 같은 값이어야 한다.** 인가 요청에 `redirect_uri`가
실려 나가고(`_createAuthorizeUrl`), OAuth 2.0은 토큰 요청에도 같은 값을 요구한다.
다르면 카카오가 교환을 거부하는데 **증상이 앱이 아니라 서버에서 난다.**

콘솔의 Redirect URI 목록에는 **등록하지 않는다.** 네이티브는 커스텀 URL 스킴을 쓰고,
그 목록은 웹(REST API)용이다.

#### ⚠️ 취소 경로가 둘이다

| 어디서 취소 | 예외 | 값 |
|---|---|---|
| 브라우저를 닫음 | `KakaoClientException` | `reason == ClientErrorCause.cancelled` |
| 동의 화면에서 취소 | `KakaoAuthException` | `error == AuthErrorCause.accessDenied` |

**둘 다 잡지 않으면 한쪽 취소에서 빨간 문구가 뜬다.** 그리고 취소는 오류가 아니므로
화면이 아무 문구도 띄우지 않는다 — `AuthFailure.oauthCancelled`를 따로 둔 이유다.
`_signInWithKakao`가 그 값을 걸러낸다.

#### 앱 키가 두 경로로 들어간다

`--dart-define`은 Dart 코드만 본다. **매니페스트의 리다이렉트 스킴은 읽지 못한다.**
그래서 Gradle 프로퍼티로 한 번 더 넘긴다.

```
flutter build apk -PKAKAO_NATIVE_APP_KEY=... --dart-define=KAKAO_NATIVE_APP_KEY=...
```

키가 없으면 스킴이 `kakao://oauth`가 되지만, `main.dart`가 SDK를 아예 초기화하지 않아
그 상태로 로그인이 시도되지는 않는다.

#### 매니페스트에는 intent-filter만 더한다

액티비티(`com.kakao.sdk.flutter.auth.AuthCodeHandlerActivity`)와 카카오톡 탐지용
`<queries>`는 **SDK가 자기 매니페스트에 이미 선언해 뒀다.** 병합 결과는
`build/app/intermediates/merged_manifest/.../AndroidManifest.xml`에서 확인한다.

⚠️ **XML 주석 안에 붙임표 둘(`--`)을 쓰지 않는다.** 파서가 주석의 끝으로 읽어
`ManifestMerger2$MergeFailureException`이 난다. `--dart-define`을 주석에 적다가 겪었다.

### 9-9. 약관 동의는 카카오 인가보다 **먼저** 받는다

#### 카카오의 동의는 우리 약관이 아니다

| | 무엇에 대한 동의인가 |
|---|---|
| 카카오 동의항목 | **카카오가 우리에게** 이메일을 넘기는 것 |
| 우리 약관 | **우리가** 서비스를 제공하고 개인정보를 수집·이용하는 것 |

카카오 화면의 동의는 카카오와 사용자 사이의 일이라 우리 약관을 갈음하지 못한다.
특히 **생체·운동 정보**는 민감정보라 다른 동의와 분리한 별도 동의가 필요하다.

⚠️ 법률 자문이 아니다. 실제 적용은 법무 검토를 받는다.

#### 순서가 핵심이다

```
[카카오로 계속하기]
  ├─ 동의 기록 있음 ──────────────→ 카카오 인가 → 서버 → 홈
  └─ 없음 → 약관(S03) → 동의 ────→ 카카오 인가 → 서버 → 홈
```

**인가가 끝나면 서버가 곧바로 계정을 만들고 이메일을 저장한다.** 그 뒤에 약관을
보이면 이미 수집한 뒤다. 그래서 버튼과 인가 사이여야 한다.

`kakao_terms_test.dart`가 `FakeOauthCodeSource.callCount`로 이것을 고정한다 —
**약관 화면이 보이는 것만으로는 부족하다.** 인가가 함께 나갔을 수 있다.

#### ⚠️ 기기 단위로만 안다 — 알려진 한계 둘

서버가 필수 약관 동의를 저장하지 않는다(`User`에 `alertConsent`뿐). 그래서 앱이
`ConsentStore`에 기록한다. 여기서 오는 한계가 둘이다.

| 상황 | 무슨 일이 일어나나 |
|---|---|
| 앱 재설치 · 기기 변경 | 이미 동의한 사람이 약관을 다시 본다 |
| 같은 기기, **다른 계정** | 동의한 적 없는 계정이 약관을 건너뛴다 |

두 번째가 더 나쁘다. 기기에 남은 기록은 "이 기기 사용자가 동의했다"는 뜻이지
"이 계정이 동의했다"가 아니다. **그래도 지금보다 낫다** — 이 작업 전에는
아무도 동의하지 않은 채 계정이 만들어졌다.

서버가 `termsAgreed` · `termsAgreedAt`을 저장하고 로그인 응답에 실어주면
판정 근거를 로컬에서 서버로 옮기는 것만으로 둘 다 사라진다. **백엔드에 요청해 둔다.**

#### `ConsentStore`를 `TokenStore`와 나눈 이유는 수명이다

로그아웃하면 토큰은 지워야 하지만 약관 동의는 남아야 한다. 남기지 않으면 같은
사람에게 같은 것을 두 번 묻게 된다.

⚠️ **둘은 같은 secure storage를 쓴다.** 그래서 `SecureTokenStore.clear()`가
`deleteAll()`이면 로그아웃이 동의 기록까지 지운다. 키를 지정해 지우도록 바꿨고,
`consent_store_test.dart`가 가짜 저장소에 둘을 나란히 태워 이것을 고정한다.
`InMemoryConsentStore`만으로는 잡히지 않는다 — 객체가 달라 애초에 섞이지 않는다.

#### 약관 화면은 카카오 SDK를 부르지 않는다

부르면 온보딩 feature가 auth의 구현을 알게 된다. **동의를 기록하고 `pop(true)`로
돌아오기만 하고**, 인가는 로그인 화면이 시작한다.

다음에 갈 곳은 `TermsNext`를 `extra`로 받아 정한다. 이 enum이 화면 파일이 아니라
`app_routes.dart`에 있는 이유도 같다 — 화면에 두면 auth가 onboarding의 화면을
import해야 한다. 기본값이 `signUp`이라 딥링크로 들어와도 기존 동작이 남는다.

#### 마케팅 동의는 화면에만 있다

`SignUpRequest`에 받을 필드가 없고, 카카오 로그인은 `{authorizationCode,
codeVerifier}`만 받는다. **로컬에도 저장하지 않는다** — 갈 곳 없는 값을 저장하면
"저장했으니 반영됐다"고 오해할 자리가 생긴다. 서버 전송은
`docs/plans/2026-08-11-marketing-consent.md`가 열릴 때 잇는다.

#### ⚠️ 위젯 테스트는 `consentStoreProvider`도 override해야 한다

9-7과 같은 함정이다. **약관 CTA를 지나는 테스트만** `MissingPluginException`으로
죽고, 다른 경로는 저장소를 건드리지 않아 멀쩡해 보인다.

#### 이메일 동의가 없으면 로그인이 항상 실패한다

서버 `toProfile`이 이메일이 없으면 `OauthEmailNotProvidedException`(403)을 던진다.
**카카오는 이메일 수집에 비즈니스 앱 전환을 요구한다.** 콘솔에서 동의항목이 켜져
있는지가 앱 코드보다 먼저다.

#### 이메일이 겹치면 서버가 자동 연동하지 않는다

`OauthUserResolver.register`가 `EMAIL_ALREADY_EXISTS`(409)를 던진다. 로그인하려는
사람이 그 계정의 주인인지 확인할 방법이 없어서다. 화면은 **이메일 로그인으로
안내한다** — "이미 가입했다"만으로는 갈 곳을 알 수 없다.

#### ⚠️ 취소는 `PlatformException`으로 온다 — 테스트가 못 잡는다

에뮬레이터에서 브라우저를 닫아보니 실제로 오는 것은 이것이었다.

```
PlatformException(CANCELED, User canceled login., null, null)
```

네이티브 `CustomTabsActivity`가 `sendError("CANCELED", ...)`를 보내고 pigeon이 그대로
넘긴다. **`KakaoClientException`이 아니다** — 그것은 SDK가 Dart에서 던지는 경우다
(리다이렉트 주소 불일치 등).

처음에 `KakaoClientException`만 잡았더니 취소가 `oauthFailed`로 떨어져
**"카카오 로그인을 마치지 못했어요"가 떴다.** 스스로 그만둔 사람에게 오류를 보인 것이다.

⚠️ **위젯 테스트로는 절대 못 잡는다.** `FakeOauthCodeSource`는 `AuthFailure`를 직접
던지므로, 그 변환이 맞는지는 시험 대상이 아니다. **SDK 경계의 예외 매핑은 실기기·
에뮬레이터에서만 확인된다** — 그래서 `KakaoCodeSource`가 무엇을 잡았는지
`kDebugMode` 로그로 남긴다. 로그가 없으면 취소인지 오류인지도 구분할 수 없다.

## 10. 프로필 탭 (S22)

### 10-1. ⚠️ 번호 — S22가 본인, S20이 타인

Figma 페이지 이름이 `S20–S21 Profile & Records`라 헷갈리기 쉽다. **정본은
`와이어프레임_최종.md`다.** 타인 프로필(S20)은 레이아웃이 같고 액션만 다르므로

### 10-2. 화면이 `/users/me`를 부르지 않는다

값은 `AuthSignedIn.user`에 이미 담겨 있다. `AuthController`가 앱에 들어올 때마다
부르기 때문이다(§9-3-2). **여기서 또 부르면 같은 요청이 두 번 나가고, 두 값이
어긋날 자리가 생긴다.**

### 10-3. ⚠️ 닉네임이 없는 이유가 **둘**이다

| `isOnboarded` | `nickname` | 그리는 것 |
|---|---|---|
| `false` | `null` | "프로필을 완성해주세요" |
| `true` | `null` | **자리표시자** — 아직 못 불러왔을 뿐이다 |
| `true` | 값 | 닉네임 |

둘을 같이 다루면 **이미 프로필을 채운 사람에게 "완성해주세요"가 뜬다.** 실제로
겪었다 — `/users/me`가 서버에 없어 404가 나자 온보딩을 마친 계정에 그 문구가 떴다.
`profile_page_test.dart`가 이것을 고정한다.

자리표시자는 **높이를 미리 잡는다.** 값이 도착할 때 아래 줄이 밀려 내려가면 화면이 튄다.

### 10-4. 잠긴 컬렉션도 자기 색을 비춘다

30칸을 전부 회색으로 그리면 **무엇을 모으는 것인지 알 수 없고**, 로딩에 실패한 것처럼
읽힌다. 잠긴 칸도 `RunPalette`의 색을 낮은 투명도(0.28)로 깐다.

투명도만으로 상태를 알리지 않는다 — 잠긴 칸에는 자물쇠 글리프가 함께 선다(§3-5).

⚠️ **자물쇠 색을 `bgBase`로 두지 않는다.** 다크에서는 읽히지만 라이트에서는 밝은
자물쇠가 옅은 색 위에 얹혀 사라진다. `textSecondary`는 두 테마에서 배경과 반대쪽으로
움직여 양쪽 다 읽힌다.

### 10-5. ⚠️ 프로필 관문은 닫히지 않는다

`showProfilePromptSheet`(`core/widgets/`)는 **스크림 · 드래그 · 뒤로가기 어느 것으로도
닫히지 않는다.** 프로필 없이는 매칭도 기록도 돌아가지 않아 앱을 쓸 수 없기 때문이다 —
안내가 아니라 관문이다. `isDismissible: false` · `enableDrag: false` · `PopScope`
셋이 다 필요하다. 하나라도 빠지면 그쪽으로 샌다.

**끌어내리는 손잡이를 두지 않는다.** 끌리지 않는데 손잡이가 있으면 고장으로 읽힌다.
닫히지 않는다는 것은 **문구가 먼저 밝힌다** — 닫으려다 안 되는 것과 처음부터 아는 것은
다르다.

⚠️ **폼에서 채우지 않고 돌아오면 관문을 다시 세운다.** `onStart`가 `push`를 `await`한 뒤
플래그를 되돌린다. 안 하면 **뒤로가기 한 번으로 관문이 뚫린다.**

⚠️ **시트의 CTA는 `AppRoutes.profileSetup`을 연다** — 첫 로그인 때와 **같은 화면**이다.
프로필을 받는 곳이 둘이면 규칙도 둘이 되고, 한쪽만 고치는 사고가 난다.

⚠️ **닫고 나서 이동한다.** 순서를 바꾸면 프로필 등록 화면 위에 시트가 남는다.

#### 왜 `core/widgets`에 있는가

홈(S05)과 셸이 함께 쓴다. 어느 feature의 `presentation`에 두면 다른 쪽이 그것을
import해야 하고 그것은 금지된 방향이다. **언제 띄울지는 부르는 쪽이 정한다** —
시트가 `isOnboarded`를 보게 하면 `core`가 인증 상태를 알아야 한다.

### 10-6. 정본에서 뺀 것 셋

| 무엇 | 왜 |
|---|---|
| 컬러 밴드 · 아우라 | 아직 색을 모으지 않은 사람이 대부분이라 깔 색이 없다 |
| 스크림 | 밴드를 빼면 함께 빠진다. 배경에 색이 없으면 어두운 판만 한 겹 더 까는 셈이라 탁해진다 |
| 대표 기록 대시보드 | 세 값이 전부 러닝 기록에서 나오는데 기록 기능이 없다. `0 km · 상위 --%`는 고장으로 읽힌다 |

팔로워/팔로잉은 자리만 잡고 **누를 수 없게 뒀다.** 서버에 기능이 없어 누르면 반응이
없고, 그것은 고장으로 읽힌다.

## 11. GPS 값 — 센서를 그대로 믿지 않는다

### 11-1. ⚠️ 안드로이드의 방향은 못 구해도 `0`이다

`Position.heading`은 방위가 없을 때 **음수가 아니라 `0`**을 준다. `hasBearing()`이
false여도 `getBearing()`은 `0.0`이다. 그래서 `heading < 0`으로 "모른다"를 걸러내려는
코드는 **안드로이드에서 아무 일도 하지 않는다.** 0을 그대로 두면 "정북"이라는 뜻이 된다.

`headingAccuracy`로도 못 거른다. 에뮬레이터에서 15개를 재보니 전부 `30.0` 고정이었다.

`0`이 아닐 때도 믿을 수 없다. 북동 45도로 움직이는 동안 받은 값이 전부
**0.005~0.011도**였다. 같은 좌표로 직접 계산하면 42~47도가 나온다.

→ **`GeoPoint.bearingTo`로 지나온 좌표에서 낸다.** GPS 오차 반경이 흔히 5~10미터라
그보다 짧은 이동으로 각도를 내면 잡음의 방향이 나온다. **10미터 이상 떨어진 가장 최근
좌표**를 찾아 거기서 낸다.

⚠️ **직전 좌표 하나와 비교하면 안 된다.** 좌표는 1초 간격이고 6분/km로 달려도 초당
2.8미터다. 직전 좌표와의 거리에 10미터를 걸면 **시속 36km로 달려야 방향이 나온다** —
사실상 전부 비게 된다. 되돌아보는 창으로 써야 한다(6분/km면 약 4초 전 좌표).

⚠️ **실기기는 아직 재보지 않았다.** 도플러 기반 방위는 쓸 만할 수 있어 센서 값을
대체값으로 남겨 뒀다. 케이블을 꽂을 수 있게 되면 `integration_test/location_raw_test.dart`를
돌려 정리한다.

### 11-2. ⚠️ 새 `GeoPoint`를 만드는 곳은 필드를 빠뜨리기 쉽다

`LocationSmoother.smooth()`가 보정한 좌표를 **새 `GeoPoint`로 만들어** 돌려준다.
`GeoPoint`에 `altitude`와 `heading`을 더할 때 이곳을 같이 고치지 않아, 두 값이
DB에 **한 번도 저장되지 않았다.**

컴파일도 통과하고 단위 테스트 448개도 전부 통과했다. 가짜 저장소가 넣은 값을 그대로
돌려주고, 보정을 통과시키는 경로가 테스트에 없었기 때문이다. **기기에 저장된 값을 눈으로
보고서야 찾았다.**

→ `GeoPoint`에 필드를 더하면 `smooth()`도 함께 고친다(7절 "함께 고쳐야 하는 짝").
→ 방향은 각도라 **선형 필터를 걸면 안 된다.** 359도와 1도의 평균은 180도다.

### 11-3. 에뮬레이터로 확인할 수 없는 것

`adb emu geo fix <경도> <위도> <고도> <위성수> <속도>` — **경도가 먼저다.**

| 값 | 에뮬레이터에서 |
|---|---|
| 위경도·고도 | ✅ 넣은 대로 온다 |
| 속도 | ⚠️ **노트 단위다.** `2.8`을 넣으면 `1.44 m/s`로 온다 |
| 방향 | ❌ 진행 방향을 주지 않는다 (11-1) |
| 케이던스 | ❌ 걸음 센서가 없다. 실기기 전용 |

### 11-4. 화면을 꺼도 좌표를 받으려면 포그라운드 서비스가 필요하다

`AndroidSettings.foregroundNotificationConfig`가 **`null`이 아니어야** geolocator가
위치 수집을 포그라운드 서비스로 띄운다. 없으면 화면이 꺼지거나 앱이 뒤로 가는
순간 Android가 갱신을 시간당 몇 번으로 제한하고, 그 구간이 좌표 공백이 된다.

⚠️ **`ACCESS_BACKGROUND_LOCATION`은 넣지 않는다.** geolocator README가 "백그라운드에서
업데이트를 받으려면 필요하다"고 적어 두어 "화면 껐으니 백그라운드겠네"로 읽기 쉽다.
Android가 보는 것은 **서비스를 시작하는 순간 앱이 포그라운드였는지**다. 사용자가
화면을 보며 시작을 누르므로 해당이 없고, 넣으면 사용자가 설정 화면에 직접 들어가
"항상 허용"을 골라야 한다(앱 다이얼로그로는 못 받는다).

| 넣는 것 | 왜 |
|---|---|
| `FOREGROUND_SERVICE` | 서비스를 띄우려면 필요 |
| `FOREGROUND_SERVICE_LOCATION` | **targetSdk 34부터 필수.** 우리는 36이라 없으면 시작에서 예외 |
| `POST_NOTIFICATIONS` | Android 13+에서 알림을 보이게 한다 |
| `WAKE_LOCK` | 화면이 꺼진 동안 **CPU**를 깨워 둔다. 화면을 켜는 `wakelock_plus`와 다른 것이다 |

⚠️ **`<service>`는 선언하지 않는다.** geolocator 패키지 매니페스트에 이미 있어
병합된다(`GeolocatorLocationService`, `foregroundServiceType="location"`).
중복이면 빌드가 깨진다.

⚠️ **`POST_NOTIFICATIONS`는 선언만으로 동작하지 않는다.** 런타임 요청이 있어야
알림이 서랍에 보인다. **못 받아도 서비스와 좌표 수집은 정상이다** — 안 보일 뿐이다.
그래서 "알림이 뜨는지"로 서비스 동작을 판단하면 안 된다.

⚠️ **끝낼 때 위치 구독을 끊어야 서비스가 내려간다.** 안 끊으면 개발 중에는 보이지
않고 **사용자가 배터리로 먼저 알아챈다.** `RunSessionController._teardown()`이
이미 한다.

병합 결과는 `build/app/intermediates/merged_manifests/.../AndroidManifest.xml`에서
확인한다 — 선언한 것이 실제로 들어갔는지, `<service>`가 하나뿐인지 보인다.

### 11-5. 걸음 센서는 권한을 직접 물어야 한다

`pedometer` 패키지는 **권한을 요청하지 않는다.** 매니페스트가 비어 있고 요청
코드도 없다 — README가 "설정에서 직접 허용해야 할 수 있다"고 적어 둔 이유다.

⚠️ **`ACTIVITY_RECOGNITION`은 Android 10부터 런타임 권한이다.** 선언만 해두면
센서가 **조용히 아무것도 주지 않는다** — 예외도 오류 콜백도 없어서 "왜 케이던스가
안 뜨지"를 한참 쫓게 된다. `permission_handler`로 앱이 직접 묻는다.

⚠️ **누적값이지 이번 러닝의 걸음 수가 아니다.** `TYPE_STEP_COUNTER`는 **기기를
켠 뒤 총 몇 걸음**인지를 준다. 두 표본의 차이로만 뜻이 생기고, 재부팅하면 0으로
돌아가 **음수가 나온다.**

⚠️ **초당 한 번이 아니다.** 안드로이드가 이벤트를 묶어 보내 몇 초씩 몰려 온다.
인접한 두 표본만 보면 1초에 3걸음 → 180spm 같은 값이 튄다. 창(30초)으로 평균을
내고 최소 구간(5초)을 둔다.

⚠️ **`DateTime.now()`를 시각으로 쓰면 안 된다.** 묶여 온 표본이 전부 같은 시각을
갖게 되어 케이던스가 무한대로 튄다. 패키지가 주는 `timeStamp`를 쓴다.

⚠️ **에뮬레이터에는 걸음 센서가 없다.** 실기기로만 검증된다.

## 12. 네이버 지도 — 로딩 배경의 흰 격자

지도에 타일이 아직 없을 때 SDK가 배경 이미지를 깐다. 그것이 **흰 격자**(`#F3F2F1`
바탕에 `#DAD9D8` 선)라 어두운 앱에서 화면이 밝게 번쩍인다.

### ⚠️ `android/app/src/main/res/drawable-*/navermap_default_background_light.png`

**이름이 SDK 리소스와 같은 것은 의도한 것이다.** 안드로이드는 앱 모듈의 리소스가
라이브러리(AAR)의 같은 이름 리소스를 이긴다. SDK가 `_light`를 고를 때 우리 파일이
쓰이게 만든 것이고, 내용은 **SDK의 `_dark` 타일을 그대로 복사**했다(`#252B30`).
색을 새로 만들지 않았으므로 격자 모양과 톤이 SDK 것과 같다.

**밀도 다섯 곳에 모두 넣어야 한다**(mdpi·hdpi·xhdpi·xxhdpi·xxxhdpi). 한 곳만 넣으면
기기 밀도에 따라 라이브러리 것이 선택된다.

### 왜 코드로 못 고치나

네이티브 `NaverMapOptions`에는 `backgroundColor`·`backgroundResource`가 있지만
**`flutter_naver_map`이 둘 다 노출하지 않는다.** 플러그인이 네이티브에서 건드리는
옵션은 `compassEnabled` `zoomControlEnabled` `scaleBarEnabled` `logoClickEnabled`
`locationButtonEnabled` 다섯뿐이다.

⚠️ **`nightModeEnable: true`로는 안 된다.** 시도했고 배경이 그대로 흰 격자였다
(에뮬레이터에서 픽셀로 확인). 커스텀 스타일과도 무관하다.

### ⚠️ 조용히 원상복귀할 수 있다

SDK가 리소스 이름을 바꾸면 우리 파일은 아무것도 덮지 않고, **에러 없이** 흰 격자가
돌아온다. `flutter_naver_map`이나 `map-sdk`를 올린 뒤에는 지도 로딩 화면을 한 번
눈으로 본다. 확인은 지도가 **처음 뜨는 순간**에만 가능하다 — 타일이 깔린 뒤에는
배경이 보이지 않는다.
